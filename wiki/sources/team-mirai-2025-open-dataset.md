## 何のデータか

2025 年 7 月の参院選で、チームみらいの「しゃべれるマニフェスト」（AI がインタビューして政策提案の PR を書く仕組み。中身は [[idobata]] のいどばた政策）に届いた提案を、広聴AI で分析した結果。各段の出力を全部残してあるので、後段だけを別の方法でやり直せる。

| 段 | 件数 | 方法 |
|---|---|---|
| 政策提案の PR | 9,688 | 2025-05-15〜07-26 の team-mirai/policy の PR。97.9% は AI インタビュアーの bot が作成 |
| 課題の抽出 | 18,967 | gpt-4o（policy-pr-hub のスクリプト） |
| 意見の抽出 | 21,348 | 広聴AI（gpt-4o-mini）、2025-07-30 実行 |
| 配置とクラスタ | 上位 20・下位 400 | 広聴AI。text-embedding-3-small → UMAP 2 次元 → 2 次元座標の上で k-means 400 → Ward で 20 に併合。表札は gpt-4o-mini |

ほかに 1536 次元の埋め込み 2 種類（広聴AI が UMAP に入れたものと、2025-10 に計算し直したもの）、取り込み可否つきの PR 表、広聴AI の実行設定（全プロンプト・パラメータ・各段のコード）、英訳（`argument_en`・`label_en`・`takeaway_en`、2026-10 にオープンウェイトのモデルで機械翻訳、人手の確認なし）が入っている。

**ライセンスは CC BY 4.0**。元の team-mirai/policy も CC BY 4.0 で、チームみらいの許可を得て公開したと README に明記されている。PR のタイトルなどニックネームが入りやすい列は除いてある。

## kouchou-ai の公開用 artifact との対応

結果 JSON の層分離の第 1 段（PR [#1179](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1179)）で入った `public_result.json` の項目（`packages/analysis-core/src/analysis_core/public_result.py` の `ARGUMENT_KEYS` / `CLUSTER_KEYS`）と、ほぼ 1 対 1 で対応する。

| `public_result.json` | このデータセット |
|---|---|
| 意見 `arg_id` / `argument` / `comment_id` | `arguments.id` / `argument` / `comment_id` |
| 意見 `x` / `y` | `umap_x` / `umap_y` |
| 意見 `cluster_ids` | `cluster_level1` / `cluster_level2`（根のクラスタは補う） |
| 意見 `url` | `pr_url` |
| クラスタ `id` / `level` / `label` / `takeaway` / `parent` / `density_rank_percentile` | `clusters` の同名の列 |
| クラスタ `value` | `num_arguments` |

足りないのは根（level 0）のクラスタだけで、全体の概要文は `pipeline/kouchou-ai-overview.txt` にある。したがって変換スクリプト 1 本で `public_result.json` の形にでき、その形を読む可視化はそのまま本体の公開ビューアの plugin に移しやすい。

## 可視化の題材としての向き不向き

- **付箋ズーム**：意見・座標・クラスタの経路・表札が全部ある。[[open-decisions]] A13 で「先に決める」としていた書き出しの取り決めを、`public_result.json` の形で代用できる。21,348 件なので 1 万件超の表示の検証にもなる
- **ツリー表示（階層リスト）**：20 → 400 → 意見 → 元の PR まで辿れる。`density_rank_percentile` で [#60](https://github.com/digitaldemocracy2030/kouchou-ai/issues/60) の「濃いクラスタだけに絞る」も試せる
- **マンダラート**（[#880](https://github.com/digitaldemocracy2030/kouchou-ai/issues/880)）：階層が [20, 400] で、マンダラートの前提 [8, 64] と合わない。11-07 の nishio の案は **8 分割を、各マスが意見 1 枚になるまで繰り返す**（8, 64, 512, … と降りる）。21,348 件なら log8 ≈ 4.8 なので 5 段前後
  - 広聴AI の既定の階層づくり（最細の段を k-means で切り、Ward で上へ併合する）では、親 1 つあたりの子の数が揃わない。このデータでも上位 20 の子の数は 1〜38（中央値 18.5）。段数を [8, 64, 512, …] と指定しても「子は 8 つ以下」は保証されない
  - したがって、上から順に「8 つ以下に割る」を再帰的に繰り返す分割が要る。子が 8 以下になった節は意見そのものをマスに並べる。木の深さは枝ごとに変わってよい
  - 内部の節は約 3,000 個になるので、全部に LLM で表札を付けると数が多い。深い段は中心に最も近い意見をそのまま表札にする手もある
  - 入れ子の 3×3 は、そのまま拡大縮小できる格子になる。付箋ズームの配置を UMAP 座標でなくこの格子にする案とも重なる
- **日英の両方で見せられる**：英訳の列があるので、海外の研究者向けにも同じデータで見せられる

## 使うときの注意（README より）

- PR の本文は市民が直接書いたものではなく、AI インタビュアーが会話から書いたもの。課題・意見はさらに 2 回の LLM 抽出を経ている
- 参加者はチームみらいの AI と話すことを選んだ人で、有権者の標本ではない
- `umap_x` / `umap_y` は同じ設定で UMAP をやり直しても再現しない（ライブラリの版と環境で変わる）。公開されている座標とクラスタを基準として扱う
- 英訳は機械翻訳。用語が大事なときは日本語の列を見る

## 位置づけ（2026-11-07 の nishio の方針）

可視化（付箋ズーム・ツリー表示・マンダラートなど）は、このデータを共通の題材にして **nishio の個人 repo で作ってカタログ化し、kouchou-ai 本体に入れるかはそこで試してから決める**。詳細は [[open-decisions]] A13。

## 個人 repo のカタログ

2026-11-07 に [nishio/broadlistening-visualizations](https://github.com/nishio/broadlistening-visualizations)（public、コードは MIT、デモは GitHub Pages）を作った。

- 変換スクリプトでこのデータを `public_result.json` の形にし、可視化はそれを読む
- 最初の項目は **意見マンダラート**（[デモ](https://nishio.github.io/broadlistening-visualizations/mandalart/)）。1536 次元の埋め込み（cosine）を上から k-means（k=8）で割り続け、5,848 節・最大 7 段（段ごとの節の数は 1, 8, 64, 509, 2811, 2279, 170, 6）。表札は各まとまりの中心に最も近い意見（LLM 不使用）で、上の段ほど「〜が不足している」のような一般的な文になる。9×9 と 3×3（スマホ）、日英の切替、最下層から元の PR へのリンク
- 同日、nishio の指示でマンダラートの既定を 3×3 にし、カタログに **付箋ズーム**（[デモ](https://nishio.github.io/broadlistening-visualizations/sticky/)）と **階層リスト**（[デモ](https://nishio.github.io/broadlistening-visualizations/tree/)）の実物を足した。どちらも `public_result.json` をそのまま読む
  - 付箋ズーム（最初の版）：画面の升目ごとに 1 枚を毎フレーム選び直す方式で、拡大すると付箋が入れ替わって震えた。オリジナルのコードを読まずに作っていた
  - 付箋ズーム（作り直した版、同日）：nishio の「オリジナルを参考にしつつ、引いた状態でも付箋で意見が見える価値は残す」という指示で、地図アプリの地名ラベルと同じ事前計算にした。位置はオリジナル（`canvas_kozaneba_prototype` の `StickyNotesZoomDemo`）と同じく格子＋螺旋で全意見を固定し（平均のずれ 0.76 マス）、拡大率を 2 倍ごとに 8 段に区切って、引いた側から優先度順（上位クラスタの代表 → 下位クラスタの代表 → 残りを全クラスタで順番に）に「重ならないなら出す」を決める。付箋は画面上で一定の大きさ。全体が 1000px の拡大率で 27 枚、16 倍で 2,058 枚、約 60 倍で全件。ブラウザで 60 段の拡大を試し、付箋の重なり 0・位置の変化 0・枚数の単調増加を確認
  - 階層リスト：本体の階層リスト（PR [#1166](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1166)）と同じ見せ方の単体版に、検索を足したもの
- 2026-11-08、nishio の「付箋に出す文字は可能な限り大きく」という指示で、マンダラートと付箋ズームの文字を **全文が収まる最大の大きさ** にした（個人 repo の commit `23a2584`）
  - マンダラート：マスごとに 10〜40px を二分探索（全マスを同じ歩みで探し、配置計算は 1 歩 1 回）。幅 1280px で 3×3 は 26〜38px、9×9 は 13〜24px でどのマスも全文が入る（以前は 13px・11px 固定で行数で切っていた）。スマホ幅の 9×9 で以前からマスどうしが重なっていたので、盤を最小幅 620px にして横スクロールにした
  - 付箋ズーム：付箋の大きさは画面上で一定なので、付箋ごとに 10〜28px を 1 回だけ決めて使い回す（寄っても文字は変わらず震えない）。表札と本文を 1 枚に入れる付箋は 140×76px では 10〜12px にしかならず、nishio の判断で **まとまりの代表の付箋は表札だけ**（濃い色・太字）にし、代表の意見の本文は押すと出るようにした。3 段寄った状態の 134 枚で、表札の付箋は 13〜18px、意見の付箋は 10〜21px（大半 13〜17px）

- 2026-11-08、nishio の「tokoroten の実験的なやつもこっちで実験して」という指示で、**対立軸ビュー**（[デモ](https://nishio.github.io/broadlistening-visualizations/divcon/)、個人 repo の commit `b18593f`）を足した。元は [[tokoroten]] の DivCon（`tokoroten/divcon`、MIT）で、段の構成とプロンプトはそのまま、LLM によるトピック発見（Stage 1・2）の代わりに広聴AI の上位クラスタをトピックにした（本体に載せるときも「クラスタごとの対立軸」になる）
  - 部分集合は nishio の「ランダムではなく適切な部分集合」に従い、賛否の割れそうなまとまり 4 つ：エネルギー（967 件）・家族（659 件、夫婦別姓・同性婚）・移民と外国人（444 件）・皇位継承（97 件）。計 2,167 件
  - LLM は組織内の OpenAI 互換 LLM（`unsloth/Qwen3.8-27B`、並列 2）。358 回・約 20 分。接続先のホスト名は追跡しない JSON から読み、repo に入れていない。この接続先では response_format の JSON Schema（制約つき生成）が空白を出し続けて止まらず、スキーマをプロンプトに書く方式にした
  - 結果：軸 12 本・延べ採点 3,338 件。移民は両側がある（例「厳格な管理 vs 包括的な受容」で左 180・右 68）。家族は一方に大きく偏り反対側は各軸 10 件ほどで、2 ペインにするとその少数側が埋もれない。再エネ推進を反原発と読むなどの誤り、中立がないので関係の薄い意見が 3・4 に寄る、「議論の活性化 vs 停滞」のように「〜が不足している」型の入力から来た軸、皇位継承の「男系 vs 女系」が 97 件中 16 件しか採点されない（立場が整えた文に残っていない。このデータセットには提案本文がない）
  - `public_result.json` に足りない項目：意見ごとの採点は `arguments[].attributes` に数値で載るが、**軸の定義（名前・両極・アンカー・合意可能性）を置く場所がない**。省略可能なトップレベルキー（仮 `opposition_axes`）を足す提案を個人 repo の README に書いた（nishio 判断待ち）

- 2026-11-08、nishio の「賛否スライダーもこっちで試して」という指示で、**賛否スライダー**（[デモ](https://nishio.github.io/broadlistening-visualizations/slider/)、個人 repo の commit `6971f97`）を足した。元は [[tokoroten]] のセンチメント次元の付与（sentiment-weighted UMAP）。賛否スコアに重みを掛けて埋め込みに 1 次元足し、重み 0〜1.5 の配置をスライダーで動かす
  - 賛否スコアは本体の任意ステップ `opinion_stance`（[#1165](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1165)）と同じ形・同じ既定プロンプト。本体は AGPL-3.0、個人 repo は MIT なので、プロンプトは写さず kouchou-ai の checkout から実行時に読む。対象は 1 レポートに 1 つなので、まとまりごとに `public_result.json` の部分集合を作って `config.question` を対象に置き換えた（エネルギー＝原子力の活用、家族＝選択肢を法的に広げること、移民＝受け入れを広げること、皇位継承＝女性・女系天皇を認めること）。組織内の LLM で 2,167 回・応答待ち 654 秒
  - 元の設定（前の重みの座標から学習率 1.0 で学習し直す）では、重みを変えなくても点が配置の幅の 12% 漂った。学習率 0.1 と Procrustes の重ね合わせで 2.5% にした
  - 重み 0 → 1.5 で、賛否の分かれ（シルエット係数）はエネルギー 0.09 → 0.73・移民 0.01 → 0.72・皇位継承 0.27 → 0.91、家族は賛成が大半で -0.02 → 0.14。話題の近さの残り（近傍 15 件の重なり）は 1〜2 割落ちる
  - 逆に「賛否を無視したら元の広聴AI になるか」（nishio の問い）も試した。重み 0 が元の広聴AI と同じ考え方で、負の重みは正と同じだけ分かれるので無視にならない。埋め込みから賛否の方向を線形に取り除くと：埋め込みには賛否がはっきり入っている（AUC 0.81〜0.93）のに、元の配置は皇位継承以外ほぼ賛否で分かれていない（-0.01〜0.09）。10 方向取り除いても AUC は 0.7〜0.8 に残り、配置は seed 違い以上に変わって話題の近さも落ちる。このデータでは、元の配置がすでに「賛否をほぼ無視した地図」で、無視の端を足しても得るものはほぼない
  - `public_result.json` に足りない項目：スコアは `arguments[].attributes.stance_score` に載るが、**何への賛否か（対象の文）が載らない**（`target` を指定すると `opinion_stance_summary.json` にしか残らない）。省略可能なキー（例 `config.opinion_stance_target` か `attribute_meta`）を足す提案を個人 repo の README に書いた（nishio 判断待ち）

- 2 つを作ってみた見立て（2026-11-08、nishio に聞かれて AI が答えたもの。nishio の判断ではない）
  - **対立軸ビューは読む道具になる**。軸に名前があり、左右に強い立場から文で並ぶので、どちら側にどんな意見があるかを追える。家族のように一方に偏ったまとまりでも、少数側が片方の欄に独立して並んで埋もれない。「合意できそうな点・根本的に対立する点」は熟議の材料になる。弱いのは採点の誤り、中立も「関係なし」も選べないこと、「〜が不足している」型の入力では立場が読めないこと、費用（2,167 件で約 20 分、全件なら約 10 倍）。賛否が割れる問いを立てたレポートで、中立と「関係なし」を足して試せば使えるものになりそう
  - **賛否スライダーは説明用で、新しく見えるものは少ない**。分かれるのは足した 1 次元（賛否スコア）が距離になるからで、分かれた島はスコアで割ったのとほぼ同じ。そのうえ話題の近さが 1〜2 割崩れる。元の配置のまま点を賛否スコアで塗り分けるだけで、話題の近さを崩さずに同じ情報が見える
  - いちばん価値があったのは副産物の「無視したら」の実験：埋め込みには賛否が入っている（AUC 約 0.9）のに 2 次元の地図では消えている（シルエット ≈ 0）。広聴AI の散布図は話題の地図で、賛否は描いていない。散布図で賛否が分かれて見えないのは賛否が無いからではない、というのは利用者に伝える価値がある
  - 2 つに共通する難しさは「何についての賛否か」を先に決めること。対立軸ビューは LLM に探させ、賛否スライダーは人が対象の文を書く（エネルギーでは原子力の活用に対して 56% が判定不能で、結果は対象の選び方に左右される）。描き方より軸を決めるほうが難しい
  - 残っている判断への AI のおすすめ：賛否の対象を置くキーは足す（本体の `opinion_stance` がすでにスコアを出しており、何への賛否かが公開ファイルに残らないのは今の欠け。省略可能なキー 1 つで済む）。軸の定義を置くキー（仮 `opposition_axes`）はまだ足さない（DivCon は本体に入る予定がなく、使う側が個人 repo だけ）。本体に入れるなら、いちばん安く効くのは公開ビューアの散布図に「賛否スコアで色分け」を足すこと。nishio はこの方向の試作を個人 repo で今は作らないと判断した
  - 対立軸ビューを誰がどの場面で使うかのユーザストーリー案（政策を書き直す人・ファシリテーター・パブコメの回答者・参加者・報告をまとめる人）は [[divcon-view-user-stories]]
