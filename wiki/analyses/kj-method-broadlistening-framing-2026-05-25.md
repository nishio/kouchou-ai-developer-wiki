# 広聴AI を KJ法の公共的な仮説形成につなぐ

[[gpt-kawakita-kj-method-broadlistening-2026-05-25]] は、広聴AIを川喜田二郎 / KJ法に接続するブレストである。  
要約すると、広聴AI を **「行政のための要約ツール」ではなく「公共圏のための KJ 的な意味生成装置」** として再定義する論考になる。  
これは技術論ではなく **目的論** であり、current `kouchou-ai` の設計判断にどう効くかをここで整理する。

## 1. 「KJ法プロンプト」を product 設計原則として読み直す

[[broad-listening-book-extractions]] は書籍 13.2.6 を引いて「KJ法 / 表札 という日本語専門用語をプロンプトに載せると labeling 品質が上がる」と整理していた。これは **prompt engineering tips** として読まれてきた。

**前提の訂正（2026-09-15）**: そもそもこの「品質が上がる」自体が未検証である。比較実験 issue [`#882`](https://github.com/digitaldemocracy2030/kouchou-ai/issues/882) が「KJ法的な言葉を prompt に入れることが本当にラベル品質を改善しているのかは、まだ比較実験として切り分けられていない」と明記しており、2026-09-15 時点で OPEN・実験未実施。以下の「読み直し」は、効果が確認された技法の意味づけを変える話ではなく、**未検証の仮説をどう位置づけるか**の話である。

しかし [[gpt-kawakita-kj-method-broadlistening-2026-05-25]] が示すのは、KJ法は単なるラベリング技法ではなく **混沌から公共的仮説を立ち上げる方法論** であり、prompt に「KJ法」と書くだけでは KJ法的 product にはならないということだ。  
つまり「KJ法 prompt を使う」ことと「KJ法的設計原則を product に通す」ことは別問題である。

書籍 13.2.6 を出発点にするなら、その背後の方法論を product 全体に展開する道が残されている。

## 2. KJ法的に見た広聴AIの 6 つの設計原則

[[gpt-kawakita-kj-method-broadlistening-2026-05-25]] が提示する原則を current `kouchou-ai` の状態に重ねると、達成度はまちまちである：

| 原則 | 内容 | current `kouchou-ai` の現状 |
| --- | --- | --- |
| 原文に戻れる | ラベル・クラスタ・要約から原コメントに辿れる | scatter / hierarchy view から原文 drill-down は実装されている。`report.html` でも保たれる |
| 既存カテゴリに当てはめない | 行政カテゴリへの自動分類は「混沌を黙らせる」 | 現状そういう自動分類はしていない。`analysis_mode=llm_grouping` でも自由クラスタ |
| 表札は AI が確定しない | クラスタ名は人間が吟味する仮説 | label 編集 UI はない。AI 生成のラベルが事実上の確定値 |
| 少数・矛盾・分類困難を残す | `unresolved_cards.md` 的な「次の問いの種」 | exhaustive partitioning が前提で、「収まらない」を表現する schema がない |
| 論点の構造を示す | 「結論」より対立・補完・因果の図解 | scatter + 階層 tree で構造は出る。対立・因果は出ない |
| 現場に返却する | 一回限りの分析で終わらせない | analysis 単位は基本 one-shot。継続関与は product 外 |

つまり「原文復帰」と「既存カテゴリ非適用」は達成、「表札の人間吟味」「少数残存」「対立・因果構造」「継続関与」は未達である。  
この棚分けは、product としての未来の枝を整理しやすくする。

## 3. ohki-shingo の公開UI要件との重なり

[[public-ui-requirements-for-broadlistening]] が整理した公開UI 7 要件と、KJ法的原則は部分的に重なる：

- **原文に戻れる** — ohki-shingo 要件の「個別意見へ drill-down」と同じ
- **少数残存** — 「少数派の声を埋もれさせない」要件と対応
- **編集可能性** — 「自治体・市民が結果を訂正できる」要件と対応する可能性

つまり KJ法的設計原則は、ohki-shingo の議論を **理論的に裏付ける枠組み** として使える。  
[[ohki-discussion-reflection-2026-05-25]] が「散布図互換の技術論から公開UI の説明責務への問い直し」と整理した構図に、本ブレストは「公開UI の説明責務とは KJ法的な公共仮説生成のことだ」という解像度を加えうる。

## 4. 「広く聴く」と「深く聴く」の緊張は product にも露出する

[[gpt-kawakita-kj-method-broadlistening-2026-05-25]] は、行政の広聴で働く 4 つの圧力を挙げている：

- 「多くの人が言っていること」を重視する
- 「既存施策に対応しやすい意見」を拾う
- 「説明しやすいクラスタ名」に整える
- 「例外的・少数的な声」をノイズとして扱う

これらは current `kouchou-ai` の設計判断にも直接効く：

- `analysis_mode=llm_grouping` は **既存カテゴリでない自由クラスタ** を作る方向で、原則を守っている
- `濃いクラスタ抽出` 機能（`digitaldemocracy2030/kouchou-ai` README）は **多数派攻撃に対する防御** として明示されており、KJ法的に重要
- 一方、`auto_cluster_defaults`（[[auto-cluster-defaults]]）の `∛n` 経験値は **視認性ベース** で決まっており、「分かりやすさ」優先のバイアスを構造的に持つ

書籍 13.4.2 が脚注で「シルエットスコア等の自動最適化を採用していない理由：利用者が見たい粒度を選べる方が実用的」と書いているのは、まさにこの緊張を product に露出させない設計判断だが、KJ法的には「見たい粒度」自体が探索対象になりうる。

## 5. 「LLM に KJ法やらせて」では届かない

[[gpt-kawakita-kj-method-broadlistening-2026-05-25]] の核心は、

> 単に LLM に「KJ法で整理して」と投げるのは避けるべきです。それでは過程がブラックボックス化し、KJ法で重視される「発想の根拠・プロセス・産物が見える」性質が失われます。

である。これは [[llm-grouping-experiment-output-2026-05-25]] が観測した「LLM grouping は top-level label では強いが scatter 互換は悪い」「分類根拠が `reason` 列にしか残らない」状況にも当てはまる。

LLM grouping の次の改良点としては、`reason` を意思決定に乗る形式で残す（cluster ごと、boundary case ごと、unresolved case ごと）ことが、KJ法的観点では重要になる。  
これは [[llm-grouping-implementation-plan]] の延長で `analysis_capabilities` の output に明示できる。

## 6. 設計判断への落とし込み（優先度低）

current `kouchou-ai` の implementation backlog に対しては、本ブレストの結論はすぐ実装に落ちる種類ではない。優先度を整理すると：

- **schema 拡張**（`representative_docs`、`boundary_cases`、`unresolved_cards`、`edge reasons`）は中期。`analysis-core` の plugin contract に乗せられる。
- **label 編集 UI** は短期にも価値あるが、view plugin 設計（[[public-ui-requirements-for-broadlistening]]）が固まってから。
- **対立・因果構造表示** は [[graph-visualization-proposal-2026-05-25]] の bridge edge `relation type` と接続できる：`contrast` `cause-effect` `same claim across clusters` は KJ法の「対立・補完・因果」と直接対応する。
- **継続関与** は product 単体の問題ではない。書籍リリース・実証実験との接続で考える話。

[[development-priority-roadmap-2026-05-23]] / [[strategic-development-order-2026-05-23]] の優先順位（Windows 配布・既知バグ・運用基盤を上位）に変更を求めるものではない。  
ただし、研究テーマ層の「広聴AI は何を最適化しているのか」という問いに対し、**「公共的仮説の生成を最適化している」** という答えの候補を 1 つ追加する。これは [[kouchou-ai-paper-draft-strategy]] / [[kouchou-ai-paper-draft-ja]] の論文執筆にも効く視座である。

## 7. graph-visualization-proposal との接続

[[graph-visualization-proposal-2026-05-25]] の bridge edge `relation type`（same claim / adjacent issue / cause-effect / contrast / boundary）は、KJ法の「対立・補完・因果」と直接対応する。  
つまり、graph visualization 提案は **KJ法的な図解化を product に落とす具体的設計** として読める。可視化と方法論が偶然合っている。

これは co-design の好機である：  
- KJ法的原則は **何を見せるべきか** の指針
- graph visualization 提案は **どう見せるか** の手段

両者を独立に成立する設計案として持ちながら、合流させる時にどちらかが歪まないかを確認するのがよい。

## Open Questions

### 2026-11-25 原文つきのカードを組み替えて表札を立て直す試作案

[川喜田研究所のKJ法解説](https://kj-kawakita.co.jp/about_kj-method/)では、ラベルを集め、集まったラベルが何を語るかを表札にし、図解と叙述を通じて仮説をつくる。広聴AIで試す価値があるのは、**原文に戻って読み直した結果、グループの境界や表札そのものが変わる**工程。5月の分業方針に沿って、広聴AIの分析結果と利用権限のある原文を受け取る別ツールで、まず一つの話題を試す。[[analysis-stance]]より。

**現行実装の確認**（2026-11-25、本体 main `afde1cb9`）。既定のパイプラインは意見抽出、埋め込み、クラスタリング、ラベル付けの順で進み、最下層の命名プロンプトはすでに「KJ法」と「表札」を使う。管理画面の「意見グループ編集」からグループ名と説明を変更できる。現在 open の [#882](https://github.com/digitaldemocracy2030/kouchou-ai/issues/882) は同じクラスタを使ったプロンプト比較の提案で、効果の検証結果は Issue に記録されていない。進行中の[出典の多対多保持 PR #1246](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1246) はカードから元コメントをたどる際に関連する。[既定ワークフロー](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/packages/analysis-core/src/analysis_core/workflows/hierarchical_default.py)、[命名プロンプト](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/packages/analysis-core/src/analysis_core/prompts/__init__.py)、[グループ編集画面](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/apps/admin/app/_components/ReportCard/ClusterEditDialog/ClusterEditDialog.tsx)より。

**試作で行う操作**

1. 抽出済み意見を一枚ずつ読み、利用可能な元コメントに戻る。複数の条件や主張を含むカードは読み手が分けられるようにする。分けたカードにも元の意見 ID・原文参照を残す。再抽出や大規模な再計算は不要。
2. 埋め込みで近い候補を提示し、人がまとめる、割る、移す、単独で残す。現行のクラスタ名は開くまで隠し、境界にある意見を隣のクラスタからも読む。束の表札を AI が提案する際は、短い文で「この束が言っていること」を書き、根拠カードと当てはまりにくいカードを示す。読み手はカードと表札を往復して修正する。
3. 表札を並べ、読み手が補完や対立、条件の違いを示す線を引く。関係にも根拠カードをひもづけ、因果を推測した箇所は仮説として扱う。最後に、読み手が原文に戻って確かめられる仮説と、次に現場で聞く問いを一つずつ書く。

**架空の例**。自治体の意見が「仕事終わりに窓口へ行けない」「オンラインなら夜に申請できる」「初回は誰かと書類を確認したい」と並ぶとする。窓口時間とオンライン化をまたいで前二者を「仕事の後でも申請できる時間帯がほしい」と束ねる。三つ目は「初回申請には書類を一緒に確認する支援が要る」と単独で残す。両方から「初回の確認支援があれば、夜の自己申請を使える人が増えるか」という聞き取りの問いが立つ。

**最小の比較**。公開可能な原文がある一つの題材で、隣接グループの意見を含めた同じ20〜30枚を使う。現行レポートと組み替えられるカードを同じ持ち時間で読み、読み手ごとに提示順を入れ替えて試す。元コメントで裏づけられる新しい論点や質問、保持できた少数の条件、根拠不足の解釈、確認にかかった時間を記録する。初期の束を見せる影響を調べるときは、カードを組み替える同じ画面で初期の束の有無だけを変える。[[experiment-methodology]]より。

**試作で確かめる問い**。現行レポートからも同じ問いが立つか。組み替えで得た仮説は、別の読み手が原文から追えるか。少数意見を読む労力に見合う発見があるか。

### 2026-11-25 推論モデルが小さな束と表札を作る案

西尾の提案は、推論モデルに検討の時間を使わせ、凝集性の高い小さな束をつくった時点で表札を付け、その束を次の統合に使うというもの。前項の手作業の試作案から、分析エンジン側に問いを移した。現行の既定経路は UMAP 後に k-means で最下層を作り、その重心を Ward 法で併合する。LLM は既に決まった下位グループや上位グループに名前を付ける。今回の案では、**表札が成立するかを統合の判断に使う**。[現行の階層クラスタリング](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/packages/analysis-core/src/analysis_core/steps/hierarchical_clustering.py)、[上位グループの命名](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/packages/analysis-core/src/analysis_core/steps/hierarchical_merge_labelling.py)より。

1. **一枚から始め、比較候補を拾う。** 抽出済み意見と既存の埋め込みを使う。元の埋め込み空間から近いカードを検索し、複数の統合候補を推論モデルに示す。束ができたら、表札の埋め込みと束内カードからの近傍を両方候補に使う。別の言葉で語られた共通点を拾えたかは、少数の題材で近傍外も照合して確かめる。
2. **束の全体を読んで表札を書き、統合を判定する。** 小さい束はカードを全件渡す。候補の全体を、立場や条件を落とさない具体的な一文で表せるかをモデルに検討させる。成立する場合はその表札と、各カードのどの記述が支えるかを返す。「申請手続き」のような話題名でしかくくれない場合は別々に残し、判断が割れる場合は保留する。ペアごとに近くても、間に一枚挟んだだけで両端を同居させないよう、統合候補全体を判定する。[[gpt-llm-pairwise-spectral-small-n-brainstorm-2026-05-25]]より。
3. **新しい表札で次の候補を探す。** 納得できる小さな束を先に確定し、束同士を合わせる際も、表札と根拠カードを読み直して新しい表札を試す。候補が競合したときは同時に比較し、成立した統合だけを適用する。成立する統合が尽きた時点で止める。束と単独カードが並ぶ結果を許し、クラスタ数・深さは結果として得る。採用した表札・子の束とカード ID・採否の短い根拠を残す。適切な表札を作れなくても補完や対立が読めるときは、束同士の関係として記録できる。[川喜田研究所のKJ法解説](https://kj-kawakita.co.jp/about_kj-method/)より着想。

**架空の例**。「仕事が終わる頃には窓口が閉まる」と「仕事から帰った夜にオンラインで届け出を済ませたい」から「仕事の後でも届け出できるようにしたい」という束を作る。「オンライン申請の項目の意味がわからず途中でやめた」と「記入例があれば自分で書ける」は「書き方がわからないと、一人では申請を進めにくい」という別の束にする。語彙が重なる二つの束を「オンライン申請」とまとめると条件が消える。どちらも具体的に説明できる上位の表札を作れない場合は、二つの束をそのまま表示する。

**試す順序**。まず同じ公開データ数十枚と同じ抽出結果を使う CLI の探索実験で、現行の木と推論モデルの木を並べる。組み方と表札生成がともに変わる試作なので、印象差だけで採用を決めない。確認するのは、束の各カードが実際に表札の根拠になるか、少数の条件が保持されるか、語彙をまたいだ発見があるか、提示順で初期の統合が変わるか、モデル実行の時間と費用。推論の強さの効果を測る場合は、同じモデル・入力・候補探索・統合規則で `reasoning_effort` だけを変える。[[experiment-methodology]]より。

### 2026-11-25 一次判定と大きな束の再検討を分けたCLI試作

「くっつける判断は軽く、まとまりが大きくなったら、なぜ一つなのかを考える」という提案を `kouchou-analyze kj-group` に実装した。本体作業ブランチ `codex/kj-bottom-up`、ローカルコミット `c808b5ae`。既存の `args.csv` と `embeddings.pkl` を入力に、元のカード同士の近傍を現在の束同士の候補へ写す。一次判定は採否、仮の表札、短い理由を返す。採用候補が既定4枚に達したら、仮の表札と全カードを別リクエストで読み直し、表札とカードごとの支持・理由を作る。本文は入力のまま保存し、根拠からカード ID で参照する。再検討で保留・否決、または表札を支持しないカードがあったときは子の束を残す。ローカルLLMの既定は一次判定 `none`、再検討 `high`。再検討は別の推論設定やモデルを選べる。

架空の窓口時間の3枚を使い、閾値を3枚にして `qwen3:4b` で検証した（`019cd4f5`）。一次判定3件、再検討1件で、2枚の束に最後の1枚を加え「夜まで窓口を開けてほしい」に統合された。再検討の3つの引用は本文と一致した。全体76.348秒、4,580トークン中3,071が再検討。同じ3枚で一次判定にも逐語引用を求めた版は、引用を言い換えたりカードを落としたりして再検討に進めなかった。別の2枚に最初から高推論を使った版では、片方だけの手段を束全体の表札に広げた。推論設定の効果と表札品質の一般化は未評価。一次記録は `raw/experiments/2026-11-25-kj-bottom-up-smoke/`、2段階版の3枚の出力 SHA-256 は `07b9de285cb9e8517a74b3fb78783d9679d7eaf41bb95a6b9570be3b058c0f0d`。比較は探索的。

論点の異なる架空の6枚も同じ埋め込みで比較した。現行方式の下位の3クラスタでは「夜にオンラインで提出したい」と「入力項目の意味が分からずやめた」が同じクラスタに入った。二段階版の初回は6枚全部を統合し、表札に夜間の窓口と入力方法という別々の論点を連ねた。一次判定11件、再検討3件、342.501秒だった。逐語引用が一致するかは確認できても、それだけで表札の意味が全カードに共通するかは確かめられない。

「同じ場面でも解決すべき問題が異なるなら分ける」という判定例を加えた比較（`e5137470`）では、3枚と2枚の束に加え、「入力項目の意味が分からずやめた」を単独で残した。再検討3件のうち2件は見送り、1件は無効引用で保留した。小型モデルは判定例から題材にない「病院」を仮の表札に混ぜたため、例の話題を一般化した。また、逐語引用の言い換えで統合を保留する問題に対し、最終版はカードID・支持の有無・理由をモデルから取得して、本文を入力から直接たどれるようにした。

カードIDで根拠を残す版（`0ca4c350`）でも、窓口時間の3枚を一次判定3件と再検討1件で「仕事の後に役所の窓口を夜まで開けてほしい」の束にまとめ、本文3件への対応を確認した。7,273トークン中5,353が再検討。同時に別の実行をしていたため所要時間は性能比較に使わない。出力 SHA-256 は `294a34eeab53edf16238b711cd77679014707b7435c5dec988946870ba07f664`。判断例を一般化した版（`c808b5ae`）で記入例と大きな字の2枚を再試行すると、例の話題は表札から消えたが、「記入例がなくても」と本文と合わない仮の表札を作った。小さな束の命名と、実データでの再検討の妥当性は今後の比較対象。
