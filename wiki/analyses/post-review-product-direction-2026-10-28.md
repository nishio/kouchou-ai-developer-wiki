## 位置づけ

nishio「これらを踏まえて何がどうなるとよいか考察したい」を受けた考察。前提となる経緯は [[retrospective-2026-10-28]]。ここでは「何を作るか」の前に **「どういう形に収束すると、いま挙がっている 5 つ（階層リスト、付箋表示、センチメント次元、DivCon、farbrain）が別々の要望ではなく 1 つの設計の部品になるか」** を考える。既存の方針（[[analysis-stance]]、[[tokoroten-algorithm-discussion-retrospective]] の 3 artifact 分離、[[cli-pipeline-experiment-roadmap-2026-06-02]] の CLI 実験場、[[plugin-system]]）を起点にし、それらと矛盾する提案はしない。

## 1. レビューの後で、問いの種類が変わった

10 月のレビュー 4 段で、修正 PR 100 本超が全部 main に入り、open PR は 0 本になった。1 万件前後の OOM と公開ビューアの重さが直り、鍵漏洩の出口も塞いだ。つまり **「壊れているものを直す」段階は一巡した**。次に効くのは、直すことではなく「何を約束する製品か」を一段はっきりさせることで、宙に浮いている 5 つはどれもその問いに属している。[[retrospective-2026-10-28]]より

同時に、レビューで分かった構造的な事実が 2 つある。

- 結果 JSON（`hierarchical_result.json`）が **分析・表示・説明のすべてを 1 つのファイルで背負っている**。鍵漏洩は「設定を丸ごと結果に書く」ことから起きたし、公開ビューアはこのファイル全体を HTML に埋め込む（3 万件で SSR 約 1GB、未修正）。view を増やすほど、このファイルに「何を載せてよいか」の契約が要る
- 公開ビューアには **可視化 plugin の仕組みが既にあり、散布図・ツリーマップ・階層リストの 3 つが plugin として並んでいる**。analysis-core 側にも `opinion_classification` のような「意見ごとに属性を足す任意ステップ」が既にある。つまり足場はあり、足りないのは「何を plugin / ステップとして足し、何を既定にするか」の判断

## 2. 5 つの要望は 2 つの軸に分解できる

| 要望 | 実体 | 軸 |
|---|---|---|
| ドリルダウンのツリー表示（階層リスト） | 同じ結果を「全部読む」ための view。plugin として移植済み | **view** |
| ズームできる付箋表示 | 同じ結果を「寄って読む」ための view。別 repo の試作 | **view** |
| センチメント次元の付与 | 意見ごとに賛否スコアを付け、埋め込みに重みを掛ける | **意見の属性**（＋埋め込みの変更） |
| DivCon | 埋め込みを使わず対立軸を作って分類する | **分析 mode**（＋対立ビューという view） |
| farbrain | 自分の投稿のハイライト、新規性スコア | **意見の属性**（＋view の装飾） |

view の軸は「同じ分析結果を、読者の目的ごとに違う形で見せる」こと。属性の軸は「意見 1 件ごとに付く情報を増やし、フィルタ・色・並びに使う」こと。この 2 軸は独立で、**属性は view を変えずに効き、view は属性が無くても成立する**。DivCon だけが分析 mode そのものを変えるので、別枠になる。

この分解で見ると、tokoroten の問題意識（同じトピックの中で賛否が混ざると洞察にならない）は、まず **属性の軸だけで最小限に答えられる**。賛否スコアが意見の属性にあれば、既存の属性フィルタで「賛成だけの地図 / 反対だけの地図」が今の散布図で見られる。埋め込みに重みを掛ける（散布図の形を変える）のは、その次の段で足りなければやる。

## 3. どうなるとよいか：「既定は散布図、目的別の view、共通の属性」

### 3-1. 既定は変えない

[[analysis-stance]] のとおり、Web UI が約束するのは「デカい見落とし・デカい違和感を見つける」こと。散布図はそのための既定であり、tokoroten の「難しいものを理解できている私」という自己効力感の読みも、投稿者側にとっての散布図の価値を裏づける。階層リストが「ウケない」のは、この既定の場面に置いたからで、view 自体の欠陥ではない。[[retrospective-2026-10-28]]より

### 3-2. view は「目的の名前」で増やす

2026-05-30 の議論で nishio は「既定の view を出した上で、反応を見て別の view を案内する」「ざっくりモードと詳細モード」を挙げた。これを plugin の並びに落とすと次になる。

| 目的 | view | 今の状態 | 次の一手 |
|---|---|---|---|
| ざっくり全体を掴む（既定） | 散布図 | 既定 | 変えない |
| クラスタの大きさを比べる | ツリーマップ | plugin あり | 変えない |
| 全部読む・掘り下げる（詳細モード） | 階層リスト | サンプル plugin | 「詳細モード」として正式化。最下層で原文・出典リンクに辿れるようにする（[#250](https://github.com/digitaldemocracy2030/kouchou-ai/issues/250)） |
| 寄って個別を読む | 付箋表示 | 別 repo の試作 | CLI の standalone HTML として同じ結果 JSON から出す |
| 配って見せる・印刷する | マンダラート | Issue のみ（[#880](https://github.com/digitaldemocracy2030/kouchou-ai/issues/880)） | CLI の静的出力として試す |
| 対立を見る | 対立ビュー | なし | DivCon の mode が結果に対立軸を持ってから |

ポイントは、view の切り替えを「手法名」ではなく **読者の目的** で見せること。truego が 2026-05-30 に「させる処理ではなく、やりたいことを選ばせる」と言ったのと同じで、「クラスタ数 30 で全部見る」ではなく「全部読む」を選ばせる。

### 3-3. 属性は「意見ごとの列」として CLI の任意ステップで増やす

`opinion_classification` が既に「意見 1 件に LLM で yes/no を付け、`attributes` に入れ、属性フィルタで使える」経路を持っている（[#971](https://github.com/digitaldemocracy2030/kouchou-ai/issues/971)）。同じ形で次を足せる。

- **賛否スコア**（-1.0〜+1.0）：tokoroten のセンチメント次元の前段。フィルタと、散布図の色として使える
- **新規性スコア**：farbrain の方式（既存の埋め込み集合からの乖離）。「少数だが珍しい意見」の候補に印を付ける。ただし「重要」とは何かはプロンプトに言語化する分析者の責務で、スコアは候補を絞るだけ（nishio 2026-05-30）
- **自分の投稿**：投稿者が自分の意見を見つけるための印。これは分析ではなく入力側の情報だが、`attributes` に載れば同じ仕組みでハイライトできる。「自分がどのクラスタにいるかわかる」要件（nishio 2025-11-04）に直接効く

属性で揃えると、view 側は「属性で色を塗る・絞る」だけを知っていればよく、view と属性の組み合わせが掛け算で増える。これが「5 つを別々の機能にしない」ための要。

### 3-4. 同じコーパスを全 view・全 mode で出したギャラリーを 1 つ作る

nishio は 2026-05-30 に「サンプルデータをいろんな手法で分析した結果がカタログみたいに見比べられるとよい」と述べた。これは 3 つの役に同時に立つ。

- **読者向け docs**：「全部読むならこれ、配るならこれ」と目的別に view を選ばせる入口になる（[[docs-persona-review-2026-10-13]] が指摘した「閲覧者向けの読み方ページ不在」に答える）
- **評価の土台**：view を比べる実験は [[experiment-methodology]] のとおり 1 要素だけ変えるべきで、同じ結果 JSON から複数 view を出すのはまさにそれ
- **実験的機能カタログ**：[[experimental-features-catalog-proposal-2026-06-03]] の「最終確認日つきで所在を固定する」を、文章ではなく実物で果たす

コーパスは公開できるものに限る。KAITO の 997 件（ローカル埋め込みで鍵不要）か、東京都の 1,000 件が候補。

### 3-5. DivCon は mode として別に設計し、view はその後

DivCon は散布図を出さない group-first の分析で、`analysis_mode=llm_grouping` の兄弟になる。[[pr-827-llm-grouping-capabilities-plan-2026-05-18]] の「分析結果の性質から使える view を判定する」考えに乗せ、結果に「対立軸」「アンカー」「スコア」を持たせる契約を先に決める。対立ビューはその契約を要求する view として後から足す。実装は tokoroten の repo の移植ではなく、`llm_grouping` のステップ構造で書き直す方が保守に乗るが、**本体に入れるか自体と主担当は tokoroten と nishio の判断**。

## 4. 順序

1. **属性ステップ 2 つを CLI に**（賛否スコア、新規性スコア）。`opinion_classification` と同じ任意ステップ。WebUI は触らない。属性フィルタで効くので、効果がすぐ見える
2. **階層リストを詳細モードとして正式化**。最下層で原文・出典リンクへ。「ウケない」仮説は、投稿者ではなく分析者の場面で測り直す
3. **全 view ギャラリー**。同じ公開コーパスで散布図・ツリーマップ・階層リスト（＋属性で色分け）を並べ、docs の入口にする
4. **付箋表示を CLI の standalone HTML に**。結果 JSON からの書き出し契約（意見・座標・クラスタの経路・表札）を決めるのが本体側の仕事で、描画は canvas 試作の知見を使う。ギャラリーに並べて散布図と読み比べる。スマホの別ビュー（[[open-decisions]] A7）を兼ねられるかもここで見る
5. **埋め込みへの重み付け**（センチメント次元の本体）。1 の賛否スコアがあって、かつ「色分けだけでは足りない」と分かってから。`sentiment_weight` だけを変えた clean experiment で、書籍の「weight=0.75 で風力発電が賛否で分離」を再現できるかを最初の問いにする
6. **DivCon を mode として**。対立軸の契約 → 実装 → 対立ビュー。評価データ（賛否が混ざるパブコメ）の確保が前提

1〜3 は AI エージェントが CLI と docs の範囲で進められ、人間の判断は「詳細モードを正式にするか」だけ。4 以降は設計判断が増える。

## 5. 守るべき制約（レビューから）

- **結果 JSON に載せるものは、出口で検査する**。属性を増やすと「意見ごとの列」が増える。鍵漏洩と同じ型の事故を防ぐため、新しいステップが書く列は `attributes` に限定し、設定や内部パスを書かない。[#1136](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1136) で入れた出口の除去をテストで維持する
- **view を増やしても、公開ビューアが結果 JSON 全体を HTML に埋め込む構造は先に直す候補**。付箋表示で 1 万件を Canvas に描くなら、データの渡し方そのものが問題になる（第 3 弾レビューの未修正指摘）
- **Web UI は既定を simple に保つ**。view は plugin、属性は任意ステップ。既定の run と既定の画面は変えない
- **merge・昇格・告知は人間**。AI が進めるのは PR・検証・ギャラリー生成まで

## 6. 反論と留保

- 「view を増やすと、結局どれを見ればよいか分からなくなる」：だから既定は 1 つで、他は目的の名前で案内する。ギャラリーで「この目的ならこれ」を実物で示す
- 「ウケないものに投資するのか」：投資は小さい（plugin は移植済み、原文リンクを足すだけ）。測る相手を投稿者から分析者に変えるのが本旨
- 「賛否スコアの精度」：LLM 推定なので誤りはある。属性フィルタで使う分には誤りが見えやすく、埋め込みに混ぜる（段 5）より安全。だから属性を先にする
- 「tokoroten の手法を AI が勝手に移植してよいか」：よくない。1〜3 は本体側の一般機能で、DivCon と埋め込み重み付けは本人の意向を先に聞く

## Open Questions

- 「詳細モード」を公開ビューアのどこに出すか（切り替えボタンか、クラスタ数が多いときの自動案内か）
- 付箋表示の書き出し契約を結果 JSON の拡張にするか、別 artifact（static HTML 用 JSON）にするか。後者なら公開ビューアの埋め込み問題を迂回できる
- 新規性スコアの定義。farbrain は Isolation Forest だが、広聴AI では「クラスタ中心からの距離」や「最近傍までの距離」の方が説明しやすいかもしれない
- ギャラリーのコーパスと置き場（本体 docs か、developer-wiki か、別 repo か）
- v5.0.0 の範囲にこれらを入れるか。書籍のリリースと合わせるなら、1〜3 だけでも「目的別に読める」という説明が立つ
