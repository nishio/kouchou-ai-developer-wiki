## 方針案（2026-11-26、西尾）

ブラウザ版とサーバ版の間の約束を、次の 1 つに絞る。

> ブラウザ版で作ったもののうち、experimental と印を付けたもの以外は、サーバ版で読むことができる。

この約束を守っていれば、両版は足並みを揃えずに、ある程度好き勝手に発展してよい。ブラウザ版の側（tokoroten）も、思いつきを experimental と印を付けて自由に投入できる。

チームの決定ではなく、西尾の方針案。[#921](https://github.com/digitaldemocracy2030/kouchou-ai/issues/921) の論点（本流にするか、所有、repo 統合）は、この案とは別に残る。

## 今の約束との違い

今の 2 版は「同じ入力なら同じように振る舞う」という振る舞いの一致を目標にしてきた。初期の適合性テストは本体の期待値と完全一致を比べ、一致しない点を既知の不一致リストに載せていた（[[serverless-integration-options-2026-11-24]]）。

方針案はこれを、**ブラウザ版からサーバ版へ、データの形だけを約束する片方向の約束**に置き換える。両版の実装の中身（抽出の仕方、クラスタの分け方、画面）は約束の外に出る。

org 版の共通契約テストは、すでにこの方向に動いている。org 版 main（`ec0c88a`）の `conformance/README.md` によると、期待値 JSON と既知の不一致リストは廃止され、Hypothesis が生成した入力で両実装の出力の性質（参照の整合、件数、公開範囲）を同じ検査器で確かめる形になった（[[serverless-shared-contract-mutations-2026-11-24]]）。

## 約束として回すために決めること

### 1. 「読める」が何を指すか

本体 main（`efbd0f28`）には、結果 JSON を受け取る入口がまだない。入力として取り込めるのは CSV だけ。したがって当面の「読める」は、利用者の操作ではなくテストで定義するしかない。候補は次の 3 段で、どこまで含めるかを決める。

- 本体の検査 `validate_output` と公開用変換 `build_public_result` を通る
- 本体の閲覧画面で描画できる
- 本体で再分析（再クラスタリングなど）の入力にできる

### 2. experimental の印をどこに付けるか

2 段に分けると扱いやすい。

- **フィールド単位**: 決まった場所（例: `experimental` という 1 つのキーの下）に入れ、サーバ版はそこを無視する。本体の `build_public_result` は「列挙していないキーは、どの深さにあっても出力に含めない」作りなので、未知のフィールドはもともと落ちる。この性質をそのまま約束に使える
- **レポート全体**: 階層や意見と出典の関係といった骨格に手を入れる時は、ファイル全体に印を付ける。印の付いたファイルは、サーバ版が読めなくてよい

ブラウザ版の書き出しは現在 `public_result.json` の schema_version 2 を出している（org 版 `src/lib/publicResult.ts`）。印のない出力は、サーバ版が対応している schema_version に限る、という形で版番号とも結び付けられる。

### 3. 昇格の時にだけ足並みを揃える

experimental の印を外す前に、サーバ版がその形を読めるようにし、共通契約テストに検査を足す。普段は別々に動き、昇格の時だけ両版の作業が要る。この手順を明文化しておかないと、印のないまま新しい形が出て約束が崩れる。

### 4. 公開範囲は experimental でも例外にしない

元コメント本文は、レポートで公開を指定した時だけ出す（[#1155](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1155)）。experimental の場所を通ってこの決まりを素通りされないよう、experimental の中身もブラウザ版の公開用変換で絞る対象に含める。サーバ版で落ちるから安全、ではなく、ブラウザ版の単一 HTML や JSON 書き出しの時点で公開範囲を守る。

## 約束に入らないもの

- **逆向き（サーバ版の出力をブラウザ版で読む）**: 方針案には入っていない。今の共通契約テストはこの方向も検査しているが、約束としては任意だと書いておくと、どこまでが約束かがはっきりする
- **振る舞いの一致**: 4 つのプロンプトの逐語一致や ward の合わせ方（[[serverless-implementation-2026-11-24]]）は、「サーバ版が読める」とは別の品質の判断になる。続けるかは、両版の結果を比べたい時に改めて決める

## Open Questions

- 「読める」を 3 段のどこまでにするか。本体に結果 JSON の取り込み口を作るなら、その時に利用者の操作としての定義に置き換える
- experimental の印の具体的な書き方（キー名、レポート全体の印の置き場所）を、ブラウザ版と本体のどちらの文書に正本として置くか
- tokoroten がこの約束を受け入れるか（org 版は tokoroten の repo の fork で、tokoroten の repo も別に残っている）
- 昇格を誰が判断するか。org 版の maintainer か、本体の maintainer か
