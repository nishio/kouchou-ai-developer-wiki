## 何を問うたか

Civic AI（[civic.ai](https://civic.ai/)）で Audrey Tang が示す「Kami」の考え方を、この developer-wiki の運用に応用できるか。

先に [[civic-ai-6pack-docs-mapping-2026-11-24]] で、6-Pack of Care の観点を広聴AI 本体の docs に当てた。今回はその対象を、この wiki を書き・保守している AI エージェントの働き方に移す。

読んだもの：civic.ai の「Set up your own Kami」（`kami.md`）と、Audrey Tang の解説「Inside the Kami」（`inside-the-kami.md`）。どちらも commit `b3013b11` 時点の版で、サイトは CC0。

## Kami とは

civic.ai の定義では、Kami は新しい種類の AI ではない。**今あるモデルに、指示（約 1,000 語）と短いメモ 3 つを足し、それを確かめ・直し・止められる人の集団が面倒を見るもの**である。仕える場所は 1 つ（町内会、教室、小さな慈善団体など）で、その場所の人に対して責任を負う。名前は神道の「神」に掛けてあり、Knowledge Artefact Management Intelligence（知識の成果物を管理する知能）の頭字語でもある（語が先で、頭字語は後付け）。

作り方のページは、次の骨組みでできている。

- **始める前の 4 つの問い**：誰が面倒を見るか（組織名でなく人の名前で）、破られたら何が損なわれるか、誰が覆せるか、いつ終えるか・見直すか。答えられなければ導入しない（「AI を使わないのも正当な答え」）。
- **制約の 3 つの置き場所**：指示で「お願い」するだけのもの、ソフトウェアが「強制」するもの、「人」が守るもの。指示は振る舞いを頼めるが保証はできないので、大事な制約は 1 つ目から 2・3 つ目へ移す。
- **ずれへの対策**：モデル・アプリ・会話の長さが変わると振る舞いが変わる。訂正はチャットでなくメモに書き、モデルを更新するたびに簡単な確認をやり直す。
- **簡単な確認**：知りえないことを聞いて「知らない」と答えるか。「どこで知ったか」に出典で答えるか。読むだけでなく書き戻すか（"A Kami that only takes will slowly drain your shared record."）。
- **却下の記録（override ledger）**：誰かが AI の提案を退けるたびに、日付・提案・退けた人の役割・理由・その後変えたことを書く。記録が途絶えたら、人が確かめなくなった兆しかもしれないので、一時停止や終了を考える。
- **Trace**：誰が面倒を見るか・何をしてよいか（強制か、お願いか）・確認の記録・却下の記録・異議の出し方・いつ終えるか、を短くまとめた公開の記録。

## 結論

- **この wiki の保守役は、ほぼ Kami の形をしている。** 既存モデル（Claude / Codex）に指示（`CLAUDE.md`）を与え、1 つの場所（kouchou-ai の開発者コミュニティ）に仕え、人（nishio）が直す。
- **重なっている所**：出典を必須にする（"No source, no sentence." と CLAUDE.md の「主張には出典を明記」）、読んだら書き戻す（filing back と「Wiki の commit / push までを完了条件」）、一部の制約はソフトウェアが強制している（lint と、公開サイトの内部リンク検査）。
- **欠けている所**は 4 つある。下の対応表と応用案にまとめた。

## 対応表

| Kami の要素 | この wiki の現状 | 判定 |
|---|---|---|
| 出典のない文は書かない | 「主張には出典を明記」、`sources:` を lint が検査 | 重なる |
| 読んだら書き戻す | filing back、commit / push までが完了条件 | 重なる |
| 大事な制約はソフトウェアへ | ページ構造とリンクは lint・CI が強制。**公開境界（デプロイ詳細・脆弱性詳細を書かない）は指示だけ** | 欠け |
| 訂正はメモに書く | AI への訂正の多くは、作業機の手元の記憶（Claude Code の memory）にある。別環境のエージェントには届かない | 一部 |
| モデル更新後の確認 | 決まった確認はない | 欠け |
| 却下の記録 | 手元の記憶と commit 履歴に散らばっている。形式は決まっていない | 一部 |

## 応用案

### 1. 公開境界を指示からソフトウェアへ移す

CLAUDE.md の規則を 3 つの置き場所に分けると、破られた時の損害が最も大きく取り消せないのが公開境界である。それが指示だけで守られている。実際、[[wiki-self-audit-2026-10-12]] では、PR-887 系の 2 ページがコンテナのログや resource サイズを公開 wiki に残していたのを、手作業の点検で見つけて消した。

機械的に検査するときの論点：

- **CI では遅い。** 公開サイトの内部リンク検査は main への push の後に走る。push した時点で GitHub 上には公開されているので、検査は push の前（作業機の git hook）で行う必要がある。
- **禁止する語そのものが秘密のことがある。** 実環境の host 名などは公開 repo の検査スクリプトに書けない。一般的な型（クラウドの host 名の形、鍵の形）だけをスクリプトに書き、具体的な語は gitignored の `raw/` に置いた一覧から読む。
- **期限つきの禁止もある。** [[user-api-key-leak-2026-10]] では、影響を受ける運用者が対処するまでの約 1 週間、問題の詳細を公開 wiki・Issue・PR・commit メッセージに書かないと決めていた。語の一覧に解除日を持たせれば、同じ仕組みで扱える。ただし、差分を見れば分かってしまう修正 PR を出さないといった判断は語の検査では捕まえられず、「人が守る」欄に残る。

### 2. 訂正を、どの環境のエージェントにも届く所に書く

Kami の作り方のページは「メモ 3 つは持ち運べるが、日々の記憶はその機械に残る」と注意している。この wiki でも、AI への訂正（たとえば「`log.md` に実在しないページの `[[...]]` を書くと公開サイトのビルドが落ちる」）が作業機の手元の記憶にしかないと、別環境で作業する Codex などのエージェントは同じ失敗を繰り返す。repo 全体に効く訂正は CLAUDE.md に移し、個人の好みだけを手元に残す。

### 3. モデルが変わったら確認をやり直す

決まった質問を 4〜5 問用意して、モデルやエージェントの更新時に流す。

- 存在しない PR や決定について聞き、「見つからない」と答え、鮮度の目印（その情報源をいつ時点まで読んだか）を示すか
- 「どこで知ったか」に、ページと読んだ時点で答えるか
- 公開境界に当たる内容を書かせようとして、Google Drive に回すか
- 読むだけで終わらず、書き戻すか

### 4. 読者向けの Trace、特に異議の出し方

この wiki は AI が書いた公開サイトである。それなのに、コントリビュータが「ここは違う」と言う経路が書かれていない。本体の docs には [[civic-ai-6pack-docs-mapping-2026-11-24]] で「止める・直す・異議を受ける」を足したが、wiki 自身に同じ穴がある。入口に数行で「誰が面倒を見ているか・AI に何を任せているか・誤りをどこに言えばよいか」を書く。

### 5. 規則にも見直し時期を持たせる

日付つきページには `status: superseded` の仕組みがあるが、CLAUDE.md の規則は増える一方である。[[wiki-self-audit-2026-10-12]] でも、同じ規則が 3〜6 回繰り返されていると指摘されていた。優先度は低い。

## 当てはまらない所

- Kami は、住民の集団が共同で面倒を見る前提に立つ。この wiki で実際に面倒を見ているのは少数の人と AI なので、「共同で守る」部分は薄い。
- メモ 3 つのうち IDENTITY.md（名前と振る舞い）に当たるものは要らない。
- 「Kami」は Audrey Tang の概念なので、この wiki の運用を Kami と呼ぶことはしない。骨組みだけを借りる。

## Open Questions

- push 前の git hook は作業機ごとに入れる必要がある。別環境のエージェントにも確実に入れてもらうには、オンボーディングの手順に足すだけで足りるか
- 期限つきの禁止で、Issue・PR・commit メッセージなど、この repo の外に書く文面まで検査する必要があるか。その場合は、エージェント側の仕組み（Claude Code の hook など）が要る
