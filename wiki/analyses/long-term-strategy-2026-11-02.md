## 位置づけ

[[nishio]]「現状を把握して、長期的な戦略を考えてみて」への回答。過去の長期整理である [[strategic-development-order-2026-05-23]]（3 層プラットフォーム）、[[broadlistening-tool-ecosystem-vision]]（simple Web UI ＋ CLI 実験 ＋ コミュニティ）、[[serverless-product-direction-2026-09-08]]（入口・重点・所有の三分）、[[post-review-product-direction-2026-10-28]]（既定は散布図、view は目的別、属性は任意ステップ）を前提にし、それらと矛盾しない範囲で、**2026-11 時点で何が変わったか** と **次の 12〜18 か月で何に賭けるか** を書く。

このページは AI が立てた叩き台であり、チームの決定でも nishio の見解でもない。決めるべきことは末尾の「戦略会議への問い」に寄せた。

> **この戦略案は AI（Claude Code）が立てた叩き台です。** チームの決定でも nishio の見解でもありません。戦略会議や Slack での議論の出発点として使い、採用・修正・却下の判断は人間が行います。nishio の指摘で既に 2 回書き直しており（柱 3）、今後も変わりえます。

## 要約

**方向性**：広聴AI を「一つの Web アプリ」から「ブロードリスニングの基盤（契約＋コア＋ビューア）」へ寄せる。機能を足すのではなく、何を約束するかを宣言し、使われ方を観測し、人間がボトルネックにならない形にする。

**根拠**：製品の形は収束し、負債は 10 月のレビューで一巡した。作る力は nishio＋AI に集中しており、OSS なので人は割り当てられない。利用の実態を測る仕組みがなく、書籍で新規流入が来る直前。コーディングエージェントが分析を完走する時代になり、価値は「契約と部品」へ移った。

**5 本の柱**

1. **書籍と同期した v5.0 を「約束の確定」として切る**（11〜12 月）。新機能ではなく宣言。stable の範囲を狭く列挙し、残りは experimental と明記する
2. **利用の観測を仕組みにする**（12 月〜3 月）。公開事例の自己申告、派生製品の一覧、pull 数、書籍読者の初見利用。印象で決めていた判断を数字にする
3. **人間がボトルネックにならない形にする**（通年）。判断を「既定＋期限」の規則に変え、AI が進め、人間は規則の決定・例外・承認にだけ関与する。branch protection を実態に合わせ、止まっても壊れない自動化と手順の checked-in を進める。人の数に依存せず、一人でも二人でも同じ規則で動く
4. **結果 JSON の層分離と、散布図を必須にしない契約**（契約は v5.0 に前倒し、丸ごと埋め込みをやめる工事は 5.x）。公開用・再分析用・説明用に分け、公開用 artifact の形を v5.0 の契約に含める。付箋表示・1 万件超・鍵漏洩型事故の再発防止・ブラウザ版との契約統一を一本で支える
5. **入口の役割分担を戦略会議で決める**。ブラウザ版・Web UI・CLI のどれを初回利用の入口にするか、ホスティング負担を法人が担うか

**やらないこと**：Web UI への複雑機能、SaaS 本番運用と DB、v4 互換のための大工事。論文は書籍後。

**成功の定義**：書籍の読者が自力で初回成功する。派生と事例が本流に戻る。人間の関与が途切れても負債が増えず、再開時に AI が wiki から文脈を復元できる。

**いま人間の判断が要るもの**：戦略会議の日程と書籍の発売日。会議で決めるのは、製品か基盤か、動けない期間の既定、ブラウザ版の位置づけ、1 年後の成功指標、書籍発売を v5.0 の期日にするか。

## 2. 診断：何が本当の問題か

### 2-a. 開発力と判断が一点に集中している

「AI で一人が 10 人分」は速いが、**判断者も一人** である。branch protection のレビュー必須は admin merge で常時バイパスされ、security の関係者連絡・リリース・merge 判断・Issue 棚卸しの承認がすべて nishio に集まる。bus factor は 1 で、谷 1〜3 はそのまま「nishio が他のことをしていた期間」と一致する。ただし対策は「人を足す」ことではない。OSS で人は割り当てられないので、**人間がボトルネックにならない形にする**、つまり判断の必要量そのものを減らし、誰がいつ関与しても進む規則にし、止まっても壊れない形にするのが実行可能な唯一の方向になる。

### 2-b. 需要が観測されていない

「階層リストはウケない」「散布図は自己効力感を作る」といった判断は Slack 上の印象に基づく。利用数・事例・派生製品を追う仕組みが無く、Discussions も無効。PyPI の数字は CLI 利用がほぼチーム内であることを示す。書籍で新規流入が来る直前なのに、**来た人がどこで何に詰まるかを観測する経路が無い**。

### 2-c. 判断の場が空洞化している

週次定例は止まり、戦略会議は未開催、[[open-decisions]] の A1〜A14 に未決が溜まる。wiki は「判断待ち」を正確に記録できるが、決めることはできない。AI は実装の速度を上げたが判断の速度は上がらず、むしろ **判断待ちの行列が伸びている**（PR 10 本、assignee 確認 8 件、本人判断 3 件、方針決定で小さく落ちるもの 7 件。[[meeting-report-draft]] の議題候補）。

### 2-d. 製品の輪郭は収束したが「約束」が宣言されていない

simple な Web UI ＋ CLI/analysis-core ＋ plugin、既定は散布図、view は目的別、属性は意見ごとの任意ステップ。この形は 2026-05 以降の整理と 10 月の実装で一貫している。しかし「何を stable と約束するか」（結果 JSON の契約、CLI と config、plugin API、対応 provider）は v5 として宣言されていない。v5 は 2026-06 目標を過ぎ、中身の大半は main に入っている。[[versioning-strategy]]より

### 2-e. 環境が変わった：コーディングエージェントが分析者になる

10-13 の Slack で nishio が「OpenAI API を置いていない環境で Claude Code に分析を頼んだら、ローカルモデルで埋め込み、自分でクラスタを命名して完了させた」と報告し、[#1175](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1175) でその進め方を docs の事例にした。分析そのものがコモディティ化すると、「広聴AI ＝ Web アプリ」の価値は下がり、**契約と部品（analysis-core、結果 JSON、ビューア、プロンプトと手順）** の価値が上がる。これは合同ミーティングで nishio が言語化した「コードの継続性の価値は低く、継続と参加の価値が希少」と同じ方向で、[[kouchou-ai]] の配布形態 B（エージェントから叩く CLI）が中心に寄ることを意味する。

### 2-f. 外部との関係に「戻る経路」が無い

派生製品（Maniken の聴くAI）、ブラウザ版（tokoroten）、チームみらいの階層リスト（本体に移植済み）、いどばた。広聴AI が基盤として振る舞うなら、派生が本流に戻る経路（契約・ライセンス・事例化・連絡先）が要る。ライセンスと出力・plugin の境界整理は [[agpl-output-and-plugin-boundaries-2026-10-12]] で済んでいるが、**派生を見つけて事例化し、必要なら本流へ還流させる運用** は無い。

## 3. 長期戦略（12〜18 か月）

中心仮説を一文で書くと次になる。

> 広聴AI を「一つのアプリ」から「ブロードリスニングの基盤（契約 ＋ コア ＋ ビューア）」へ寄せ、いま nishio＋AI に集中している作る力を、人が入れ替わっても続く体制に変換する。

成功の定義は Issue 消化数や機能数ではなく、(i) 書籍の読者が自力で初回成功する、(ii) 派生・事例が本流に戻ってくる、(iii) 人間の関与が途切れる期間があっても負債が増えず、再開時に AI が wiki と log から 1 日で文脈を復元できる、の 3 つにする。「人が増える」は成功の定義にも計画の変数にも入れない。OSS では人をアサインできず、貢献者は需要から自然発生するものだからである。

### 柱 1：書籍と同期した v5.0 を「約束の確定」として切る（2026-11〜12）

- **中身は新機能ではなく宣言**。stable と約束するものを列挙する：analysis-core の CLI・config・結果 JSON の契約、plugin 契約 3 軸（入力・解析・可視化）、対応 provider、公開境界（出口での secret 除去）。それ以外は experimental と明記する（[[experimental-features-catalog-proposal-2026-06-03]] の「最終確認日つき」をここで実装する。[#1174](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1174) の関連研究ページが先例）
- **手順**：open PR 10 本の merge → RC タグ → ペルソナによる docs・公式ページのレビュースプリント（[[docs-persona-review-2026-10-13]] の 7 像を再利用）→ 書籍の発売日に v5.0.0。analysis-core を 1.0 にするかは別判断
- **併せて決める**：v4 系の保守ブランチを作るか（これまで無し）、メジャー・マイナーの基準の明文化（[[versioning-strategy]] の Open Question）
- **受け皿**：書籍から来た人の質問・事例の置き場（GitHub Discussions を有効にするか、Slack を入口にするか）。費用・PII・相談先・責任の所在のページ（ペルソナレビューの指摘）を v5 までに揃える

### 柱 2：利用の観測を仕組みにする（2026-12〜2027-03）

- 「ウケる／ウケない」を印象で決めない。測るものを決める：公開レポートの自己申告登録（[#564](https://github.com/digitaldemocracy2030/kouchou-ai/issues/564) の公開事例ページ）、派生製品の一覧（最終確認日つき）、PyPI と Docker イメージの pull、docs のアクセス、初見利用の観測（[[serverless-product-direction-2026-09-08]] の「初見利用の評価」を書籍読者で実施）
- アプリ内の利用統計は公開境界とプライバシーの観点で慎重に扱う。まずは人手の登録と公開情報の追跡で始め、必要なら opt-in を検討する
- 階層リスト「詳細モード」の計測（[#1159](https://github.com/digitaldemocracy2030/kouchou-ai/issues/1159) の open question）をこの枠に置く。測る相手は投稿者でなく分析者
- 2026-06 に未決のままの自治体利用者課題調査を、書籍の流入期に小さく実施する

### 柱 3：人間がボトルネックにならない形にする（通年）

前提：OSS では人をアサインできない。だから計画は、人間が誰で何人いるかに依存しない形で書く。希少資源は人間の注意であり、それが誰のものであれ、「規則を決めること」と「例外」にだけ使い、進める作業は AI が担う。目的は「nishio 一人で回す」ことではなく、**人間が誰であっても、何人であっても、ボトルネックにならない** こと。結果として一人でも回るし、二人目が来ても同じ規則で動ける。初稿の「判断者を複数にする」は撤回した。

- **判断を「既定＋期限」の規則に変える**。いま人間の返答待ちになっているものの多くは、規則にすれば AI が消化できる。例：assignee 確認は期限後に既定処理（11-16 ルールとして実施中）、停滞 Issue は Cold List ルール（[#1177](https://github.com/digitaldemocracy2030/kouchou-ai/pull/1177)）、CodeRabbit の Minor は merge 後に後追い、Dependabot は CI green なら自動 merge、「方針決定で小さく落ちるもの」は「N 日以内に異論がなければ案 A」と Issue に書いて期限を切る。人間は規則を決める時と、規則に当てはまらない例外の時だけ呼ばれる
- **branch protection を実態に合わせる**。レビュー必須は常時 admin merge でバイパスされており、人間の承認を「見せかけ」で要求する偽の冗長性になっている。required check を CI ＋ CodeRabbit に変え、人間の承認は規則で定めた範囲（release、契約の変更、security）に限る。設定変更は管理権限を持つ人なら一度で済む
- **止まっても壊れない自動化**。人間の関与が途切れる期間に増えるのは依存の脆弱性・上流のメジャー更新・Issue の放置の 3 つなので、Dependabot の自動 merge、lock なしインストールの CI job（議題候補にあるもの）、月次の Issue 棚卸し workflow、の 3 つを入れる。人が見ていなくても負債が積み上がらない状態を作る
- **手順を repo の中に置く**。security の連絡と Advisory の手順、リリースのチェックリスト、棚卸しの手順を skill や docs として checked-in にし、AI が実行して、その時いるメンテナが承認するだけにする。手順が特定の人の頭の中にあると、その人がボトルネックになる。今回の鍵漏洩対応と v4.2.0 で実際にやった手順が素材になる。wiki に判断の履歴を残す運用（[[wiki-driven-workflow]]）はその一部で、再開時の文脈復元はここに依存する
- **貢献の入口は「下げる」だけで「期待しない」**。AI 向けの Issue 整形、AGENTS.md と skill の整備、「自分のトークンで AI に PR を作らせる手順」を contributing に書く。誰かが来た時に、その人の注意もボトルネックにならないための整備であって、来ることを計画の前提にはしない
- **最終手段としてのフォーク可能性**。書籍 10 章の「dd2030 が止まってもコードは残り、誰かがフォークして引き継げる」を担保するのは、人ではなく柱 1 の契約の宣言と、docs・wiki の完全性である
- **定例の再定義**。週次定例は事実上止まっており、同期の会議は人間の時間を最も消費する形式でもある。月次の非同期報告（[[meeting-report-draft]] を月次に rotate）＋ 年 1 回の戦略会議に変え、議事メモ Doc を続けるか止めるかを明示する。決めるのに会議を要しない

## 7. 反論と留保

- 「一人＋AI で回っているのだから壊すな」：壊さない。柱 3 は人を足す話ではなく、いま人が手で捌いている判断を規則と自動化に移して人間がボトルネックにならないようにする話で、実装の体制は変えない
- 「観測は手間」：最初は人手の登録と公開情報で足りる。計測基盤を作るのは数字が意思決定に使われると分かってから
- 「v5 を切ると互換責任が生まれる」：だからこそ約束の範囲を狭く宣言する。experimental を明記することが v5 の主目的
- 「戦略会議は年 1 回の儀式」：今回は書籍という入口の変化と時期が重なる珍しい機会で、ここで決めないと次は 1 年後になる
- 数字の読みには限界がある。commit 数は squash merge の影響を受け、PyPI の数字は CI の pull を含む。傾向の判断には使えるが、精密な比較には使わない
