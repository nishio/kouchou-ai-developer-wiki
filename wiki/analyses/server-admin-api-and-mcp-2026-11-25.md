## 現行の実装

2026-11-25 に GitHub の `main` と同じコミット `afde1cb9` のローカルコード、および公開 Issue・open PR を確認した。[[source-code]]の管理用 FastAPI は、レポートの一覧・作成・複製・工程別の進捗確認・公開設定変更・削除・元コメントの CSV 取得をすでに提供している。管理 UI はこの API の利用者の一つで、サーバー上にあるレポートを確認・操作できる点が、手元で分析する CLI と異なる。[[architecture-overview]]、[[analysis-core-and-web-ui]]。

- 一覧は状態と公開範囲を返し、進捗 API からは工程と推定コストを取得できる場合がある。進捗 API は内部ファイルを読むポーリング用で、エラー時には診断ログの抜粋やパスも返す。外部向けには必要な項目を選び、状態・失敗分類・未取得時の意味を定める。[管理 API の実装](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/apps/api/src/routers/admin_report.py#L282-L328)
- 作成・複製は処理を起動し、完了は後から確認する。現在はルート宣言では `202` だが、成功時の実レスポンスは `200`。外部契約として文書化する際には、まず現行仕様と期待する応答を照合する。[作成・複製の実装](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/apps/api/src/routers/admin_report.py#L96-L179)・[現行テスト](https://github.com/digitaldemocracy2030/kouchou-ai/blob/afde1cb9a19cb8471fc353b54ae07a4710336299/apps/api/tests/routers/test_admin_report.py#L579-L593)
- 既存の認証は単一の管理キーで、参照と公開設定変更・削除に同じ権限が使われる。管理画面内でのキーの扱いは既存の議論に委ね、外部連携に渡す権限は新たに定義する。[[admin-api-key-threat-model-2026-11-11]]・[Issue #1197](https://github.com/digitaldemocracy2030/kouchou-ai/issues/1197)

## 提案

1. **既存 FastAPI の一覧・進捗を、外部から使える管理 API として提供する。** 「昨夜の分析で失敗した案件と止まった工程を知る」を最初の運用例にする。既存のレポート状態を読み、実行状態と公開範囲を別の項目として返す。必要に応じて推定コスト、安全な失敗分類を返す。参照用の資格情報で参照だけを認可し、元コメント・設定の全文・診断ログは応答の対象外とする。フィールド、エラー、互換性を文書化し、実際の HTTP 応答をテストで固定する。まずスクリプトでこの運用例が通ることを確かめる。
2. **MCP を任意で使えるようにし、同じ参照操作を提供する。** 初版は `list_reports` と `get_report_status` を想定する。チャットから「失敗分の状況と次に確認すること」を聞ける。アダプターは管理 API の参照用の認可を使い、対象と項目を限定した構造化データを返す。リモート接続を提供する段階で、利用者・クライアントごとの認証と権限を設計する。[MCP Tools 仕様](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
3. **生成を繰り返す利用者がいれば、非公開レポートの作成を追加する。** たとえば定期集計では、同じ設定で非公開レポートを作って完了を待ち、人が公開前にレビューする。受付時に追跡用の ID を返し、再送で同じ分析を二重に実行しないようにする。公開と削除は独立した権限とし、MCP 経由で追加する場合は対象を示した明示確認と操作記録を設ける。

## Updates

### 2026-11-25 読み取り専用の試作を実機確認

- 本体 `codex/admin-read-api-mcp`（`5b2d756f`）で `GET /admin/v1/reports` と `GET /admin/v1/reports/{slug}/status` を追加した。一覧は失敗分に絞れ、進捗は実行状態・分かる範囲の工程・推定費用を返す。工程は原因の診断と区別し、成果物の同期で失敗した場合など、該当する工程が分からないときは `null` になる。
- 専用キーを設定したときだけ有効。非公開レポートも含む一覧と進捗に権限を限り、元コメント、設定、診断ログは応答に含めない。任意の stdio MCP は同じ API を `list_reports` と `get_report_status` で呼ぶ。起動例は本体 `apps/api/README.md` に記載した。
- 架空データで起動したローカル API と MCP の JSON が一致し、読み取りキーで削除が拒否されることを確認した。API 594 テストと Ruff が通過。次に運用で試すなら、失敗一覧と工程情報だけで担当者が調査に着手できるかを見る。
