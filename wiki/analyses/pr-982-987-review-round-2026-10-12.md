## #987 の BLOCKER と追修正（commit 8a09108e）

### 症状
`analysis_mode=llm_grouping` のレポートを作成後、admin の設定編集（タイトル/問い変更）
→ 再集計で **`TypeError: 'NoneType' object is not iterable`** により集計が error status。
hierarchical レポートは無影響。

### 原因（なぜ既存の prune では防げなかったか）
PR #987 は `ReportConfig` に hierarchical 専用・llm_grouping 専用セクションを
両方 known field として持たせ、`prune_config_for_mode`（commit 73756f21）で
mode 非該当セクションを落とす設計を入れた。しかし prune は **「非該当 mode の
セクション」だけを削除し、active mode 自身の `None`/空セクションを残していた**。

- 作成フローの `_build_config` は llm_grouping セクションを**省略**して analysis-core の
  既定に委ねる → 初回 config file には `llm_grouping` キーが無く、初回実行は validate OK。
- 編集で `ConfigRepository.update_json` が `read_from_json().model_dump()` を通すと、
  `ReportConfig.llm_grouping` の既定 `None` が顕在化して **`llm_grouping: null`** を書き戻す。
- prune（mode=llm_grouping）は hierarchical 専用セクションのみ落とし `llm_grouping: null` を残す。
- analysis-core の `core/orchestration.py:273` `for key in config.get(step_spec["step"], {})`
  は、`llm_grouping` が step 名に含まれ値が present-but-`None` のため、
  `config.get("llm_grouping", {})` が `{}` ではなく `None` を返し → `for key in None` で TypeError。

### 修正
prune で **active mode 自身のセクションも値が `None`/空なら削除**し、analysis-core の
既定に委ねる挙動へ戻す（値入りセクションは温存）。値入り判定で keep/drop を分ける
ため `ALL_MODE_SECTIONS` を導入。

回帰テスト（この gap が blocker を見逃した原因＝「llm_grouping レポートの `None`
round-trip」が未カバーだった）:
- prune の unit（llm_grouping / hierarchical 両方の null・空 active セクション削除、
  値入りは温存）
- **llm_grouping レポートの `update_json` round-trip** が `llm_grouping: null` を
  書き戻さず、実 `analysis_core.validate_config` を通過すること

### 検証（before/after）
隔離 venv で analysis-core を editable install し確認:
- **旧 prune** → `validate_config` が `TypeError`（blocker 再現）
- **新 prune** → `llm_grouping` キーを drop → `validate_config` 通過
- `test_analysis_config.py` 13 passed、prune consumer 系（launcher/duplicate）31 passed、
  ruff check / format クリーン

> follow-up 候補（本 PR 外）: analysis-core 側 `core/orchestration.py:273` を
> `config.get(step, {}) or {}` にすれば、present-but-`None` セクション全般に対する
> 防御が analysis-core 単体でも効く。今回は PR スコープを API 境界の prune に限定した。

auto-merge 不能な衝突（`ScatterChart.tsx` の customdata/onClick、admin create の共有 8 ファイル）
を踏まないため。
